# Задачи — список с чатом по каждой задаче

Список задач и проектов, где задачу можно закрыть галочкой, а можно «толкать вперёд» перепиской. Большие задачи становятся проектами: в списке видна одна строка проекта со следующим шагом.

Живёт на GitHub Pages: https://cucujahx-coder.github.io/CLUTCH/

## Стек и запуск

- Статические файлы, **сборки нет**. Ванильный JS, без фреймворков и рантайм-зависимостей. Все иконки — inline SVG через `I(name, size, colorVar)`, пиксельные рисунки 8×8 в `P`.
- `npm start` — раздать папку локально. `npm test` — тесты приложения (jsdom) и воркера. По отдельности: `npm run test:app`, `npm run test:worker`.
- Проверка синтаксиса без запуска: `node --check app.js`.
- Деплой: `git push` в `main` → `.github/workflows/deploy.yml` гоняет тесты и выкладывает на Pages. В артефакт файлы перечислены явно — **добавил новый файл, допиши его в шаг «Собрать сайт»**, иначе на проде его не будет. Папка `worker/` на Pages не выкладывается и не должна: она разворачивается отдельно в Cloudflare.

## Две оболочки, один движок

`index.html` (два экрана: задачи и чат) и `panels.html` (две панели рядом) — тонкие обёртки вокруг общих `app.js` и `app.css`. Оболочка задаёт `window.MODE` (`nav` | `two`) перед подключением скрипта, `app.js` по нему выбирает `shellNav()` или `shellTwo()`. Различий ровно три: класс на `<body>`, кнопка «назад» и функции `open`/`back`. Вид отличается вводом. В `panels.html` поля ввода `.ft` — отдельные плашки под панелями внутри `.scr`. В `index.html` оба поля — «Новая задача» и «Спросить Claude» — лежат внутри своих панелей и прилипают к их низу поверх содержимого (`.pnl > .ft`: полупрозрачный фон с размытием, у `#list` и `#thread` снизу запас на высоту поля).

В `index.html` экраны лежат друг над другом, переход — CSS по классу `.on`: чат выезжает справа налево поверх списка, список сдвигается влево и притеняется (`--scrim`, `--shadow-edge`); ушедший экран по окончании движения получает `visibility:hidden`, чтобы в него не попадал фокус. Фокус при переходе ставится с `preventScroll`, иначе браузер сдвигает `.grid` к экрану, который ещё за краем. Назад — стрелка, Esc или свайп вправо от левого края (`armSwipeBack`, зона `EDGE` = 28 px): пока палец ведёт, класс `.drag` выключает переход и экраны двигаются инлайновым `transform`; отпустили дальше трети ширины или быстро — `back()`, иначе чат возвращается. Инлайн и `.drag` снимаются в одном кадре, поэтому переход доигрывает от текущего положения. Вертикальное движение от края — прокрутка ленты, не свайп.

Логику писать только в `app.js`. Если правка нужна в обоих файлах — почти наверняка она на самом деле в движке.

## Модель данных

Всё состояние — один объект `S`, целиком в `localStorage` под ключом `tasks:v1`.

```js
S = {
  seq,                       // счётчик id, общий для задач и проектов
  ts: [{                     // задачи и шаги проектов — одним списком
    id, t,                   // t — название
    due: "YYYY-MM-DD"|null,
    pj: id|null,             // id проекта, если это шаг
    done: 0|1, doneAt,
    kind: 'task'|'reminder'|'routine'|'call'|'meeting'|'payment'|'purchase'|'mail'|'idea' | undefined,
                             // тип задачи (подпись для диктора); нет поля — угадывается по названию (kindOf)
    tail: {k:'art'|'wait'|'dec', x} | null,   // подпись-состояние в строке
    file,                    // вложение (демо)
    n,                       // счётчик сообщений для подписи
    a,                       // последняя реплика ассистента, показывается вверху чата
    chat: [{u}|{a}|{typing}]
  }],
  pr: [{ id, n, due, why, chat }],            // проекты; n — название, why — «что мешает»
  showDone, cur: {k:'t'|'p', id}
}
```

- `pj` хранит **id** проекта, не индекс: индексы ломались бы при удалении.
- `done` меняется только через `mark(x, done)` — он же ставит и обнуляет `doneAt`.
- `OLD_KEYS` — ключи приложений-предшественников (`clutch:v5` и старше). Если `tasks:v1` пуст, `importOld()` один раз перечитывает их и раскладывает в новую модель. Меняешь ключ — допиши старый в этот список, иначе у людей молча пропадут задачи.
- `save()` дебаунсит запись на 120 мс, `flush()` пишет сразу; `flush` висит на `pagehide` и `beforeunload`.
- Первый запуск без данных — `seed()`, демо-набор с датами относительно сегодня.

## Ключевые механики

- **Логотип** — в шапке списка обеих страниц три строки, как в шапке чата: сверху иконка входящих (`#brand-ic`, та же, что «без проекта»), под ней надпись «CLUTCH» (`.logo`) пиксельным шрифтом, под логотипом «Входящие»; счётчик на линии «Входящих» у правого края. Размер `--fs-logo` 24 px, на экранах ×3 — 26⅔ px (кратно пикселю шрифта), межбуквенный интервал — один пиксель шрифта. Нажатие на логотип не переключает список.
- **Входящие ↔ Выполненные** — отдельного раздела «Выполненные» внизу списка нет. Нажатие на шапку списка `#inbox` переключает `S.showDone`: список показывает только выполненные задачи, заголовок и счётчик меняются; повторное нажатие возвращает входящие. Добавление задачи возвращает к входящим.
- **Подпись строки** (`sub(x, gaps)`) — состояние или «без диалога» (нет сообщений и нет `tail`), затем срок или «без срока». Пустоты пишутся только в основном списке (`gaps`), у шагов в чате проекта — нет. Появилось первое сообщение — «без диалога» уходит.
- **Маркер строки и тип** — слева от названия у каждой строки основного списка знак «>» тем же пиксельным шрифтом (`.ki::before` — в CSS, чтобы знак не попадал в текст названия и в тесты; цвет `--text-muted`, ширина `--ki-w` — ширина знака в шрифте), подпись под названием сдвинута ровно под текст. Сам знак сдвинут `left` (relative, раскладку не трогает) так, что его середина стоит под серединой иконки в шапке списка; фактический размер иконки движок кладёт в `--hd-ic`. Строки `#list` растянуты на всю ширину панели (отрицательный отступ на ширину падинга `.bd`; внутренний справа 16, слева 32 — задачи отодвинуты от левого края), подсветка выбранной строки идёт от края до края. Тип записи всё равно вычисляется — для скрытой подписи диктору и `data-kind`: таблица `KIND` (задача, проект, шаг, напоминание, рутина, звонок, встреча, оплата, покупка, письмо, идея), `kindOf(x, isP)` — проект и шаг по структуре, иначе явное `x.kind`, иначе первое совпадение из `GUESS` по словам названия, иначе задача. У шагов в чате проекта маркера нет.
- **Строка проекта** — показывает следующий открытый шаг, кольцо рисует прогресс и закрывает именно этот шаг. Закрыли последний — строка проекта уезжает из списка анимацией `boomRow`.
- **Анимации** — плавные, с отскоком. Кривые заданы дважды и должны совпадать: `EASE` в `app.js` и `--ease-bounce` / `--ease-out` в `app.css`. Всё движение из JS идёт через `anim(el, keyframes, options)` — при `RM` и там, где нет `animate` (jsdom), она ничего не делает, поэтому тесты видят только конечное состояние. `popIn` — появление с отскоком: новая задача и новый шаг, новые реплики в чате (лента пересобирается целиком, поэтому новые элементы вычисляются сравнением с прежним числом в той же карточке — `threadKey`), строки при переключении «Входящие ↔ Выполненные» лесенкой. Выполнение — исключение, оно резкое идёт по очереди и почти мгновенно — меньше 0,1 с; тайминги — константы `T_SHAKE` 32, `T_GONE` 48, `T_COLLAPSE` 32, `T_FLASH` 80 в `app.js`. `bang(el, text)` при нажатии: `bangSound()` (хлопок петарды, синтез Web Audio — шум с резким спадом, низкий «бум» и искры; `AudioContext` создаётся при первом нажатии, в jsdom его нет — ничего не делает) и `zap(text)` сразу — текст (`.cel` строки или `#ct` в шапке чата) белеет со свечением (`.zap`: белый цвет и `text-shadow` на элементе и всём внутри) и трясётся 2 рывками по кадру ±6 px за 32 мс (`steps(1,end)`); после тряски `flash(el)` — белый фон только у выполняемой строки `.row`, а у кружка в шапке — у `.hd` (20 мс белый, гаснет к 80 мс; анимируется фон, а не накладка — иначе не видно текст). `boomRow` через 48 мс схлопывает строку за 32 мс без отскока, колбэк через 90 мс. При `RM` нет ни тряски, ни вспышки, звук остаётся. `bang` зовётся в обработчиках кружка задачи и кольца проекта; у последнего шага кольцо только пружинит (`boomSpot` с пустым колбэком), а строку проекта сразу уводит `boomRow`, чтобы расписание было тем же. `parts` (14 частиц, 120 мс), `boomSpot` (удар кружка 1.4→1 за 60 мс, колбэк через 60 мс). Переход между экранами в `index.html` — CSS, без отскока: у полноэкранной панели перелёт открывает щель у края. Меню действий появляется с отскоком и уходит плавно; уход держит последний кадр (`fill:forwards`), поэтому перед новым показом `stopAnims` его снимает — иначе меню откроется прозрачным. Нажатие на кнопки и кружки — CSS-переходы с тем же отскоком; при `prefers-reduced-motion` переходы обнуляются.
- **Высота окна и клавиатура** — `.app` это `position:fixed; top:var(--vvtop); height:var(--vh)`, то есть контейнер приложения равен видимой области. Композер лежит на его дне и оказывается над клавиатурой сам.
- **События iOS — вспомогательный сигнал, а не источник истины.** `trackVH()` сверяется с фактическими размерами каждый кадр, пока идёт ввод **или пока клавиатура на экране** (`innerHeight - visualViewport.height > 80`). Второе условие ключевое: оно не даёт застрять в поднятом состоянии, даже если событие не пришло — а при скрытии клавиатуры их может не прийти ни одного, и раскладка оставалась поднятой, накладывая блоки друг на друга. Цикл останавливается сам, когда высота вернулась. Вне ввода — обычные события (`resize`, `scroll` у `visualViewport`, `resize` и `orientationchange` у окна).
- **Значения — чистая функция текущего состояния**, без накопленных дельт: пропущенное обновление не оставляет следа. Это то, что в прошлых версиях ломалось чаще всего.
- **Тупики, проверенные на устройстве.** Первый: поднимать композер на вычисленную высоту клавиатуры (переменная `--kb`, трансформа плюс запас снизу у списка) — поле «гуляет», потому что высота клавиатуры не описывает реальный сдвиг. Второй: не компенсировать смещение вовсе — шапка и список уезжают выше края экрана. Третий: обновлять смещение только по `resize` — оно протухает. iOS панорамирует при фокусе (`offsetTop` становится, скажем, 186), а возвращает в ноль уже событием `scroll`; контейнер остаётся опущенным, и композер уходит под клавиатуру. Проверено снимком с телефона: `offsetTop 0` при `--vvtop 186px`.
- **Низ содержимого держится на месте.** Когда область ужимается под клавиатуру, `trackVH()` сдвигает `scrollTop` всех `.bd` ровно на разницу высот — иначе список и лента съезжают вверх на высоту клавиатуры и прячут то, что было у поля ввода. Перед правкой прокрутки читается `offsetHeight`, чтобы браузер применил новую высоту: иначе `scrollTop` обрежется по старым размерам. У ленты переписки распорка `.thread::before{flex:1 0 auto}` — короткий разговор стоит у поля ввода. **Список задач начинается сверху и прижимать его не надо**: пробовали, владелец вернул как было. Распорка, а не `justify-content:flex-end`: последний ломает прокрутку, верх содержимого становится недостижим.
- **Как отлаживать.** Открыть страницу с `?debug` — поверх интерфейса появятся живые числа: размеры окна и видимой области, смещение, значения переменных, положение контейнера и композера, элемент в фокусе и трасса последних значений `offsetTop` с буквой события (`r` — resize, `s` — scroll, `i` — старт). Снимок экрана с открытой клавиатурой отвечает на вопрос сразу; словесные описания дважды приводили к половинчатым правкам.
- **Что не делать с клавиатурой.** Грабли, на которые наступали:
  1. Переход (`transition`) на движении композера. `visualViewport` шлёт `resize` десятками за время выезда клавиатуры, анимация гонится за новой целью и не успевает встать.
  2. Подгонка `scrollTop` на каждом событии — список идёт ступеньками.
  3. Прятать и телепортировать поле на время фокуса, чтобы iOS не прокрутил страницу к нему (был такой `focusNoPan`): поле мигало на каждом тапе.
  4. `window.scrollTo(0,0)` при фокусе — борется с панорамированием, которое и так учтено через `--vvtop`.
- В обоих HTML у viewport стоит `interactive-widget=resizes-content`. Где поддерживается, слой раскладки ужимается сам и `--vvtop` остаётся нулём; где нет — работает модель выше. Одно другому не мешает.
- **Клавиатура на телефоне** (`shellTwo`, только `panels.html`) — по `focusin` панель с активным полем разжимается на весь экран классами `kb-list` / `kb-detail`. Поля `type=date` из этого исключены, иначе выбор даты дёргает раскладку. Свёрнутая панель получает `visibility:hidden`, поэтому программно сфокусировать поле в ней нельзя — это не баг, а следствие.
- **Меню действий** — открывается долгим нажатием по строке в списке (`armLongPress`, 500 мс — столько же держит iOS до своего меню; сдвиг больше 10 px считается прокруткой и отменяет). Правая кнопка мыши открывает то же меню. Состав зависит от строки: у задачи «Срок / Сделать проектом / Удалить», у шага проекта «Срок / Удалить», у проекта «Срок / Добавить шаг / Удалить проект». В карточке задачи никаких кнопок действий нет и быть не должно — их оттуда убрали намеренно.
- **Два подводных камня меню.** Первый: оно открывается, пока палец ещё прижат, и следом придёт `pointerup` с кликом по подложке — поэтому нажатия в первые 400 мс после открытия игнорируются (`menuAt`), иначе меню схлопывается сразу. Второй: после долгого нажатия приходит обычный `click` по строке — его гасит `suppressRow`, который сбрасывается следующим `pointerdown`.
- **Добавление шага и удаление** — без `prompt()` и `confirm()`: системные диалоги в standalone-режиме на iOS ведут себя непредсказуемо. Шаг вводится полем прямо в списке шагов (Enter добавляет и оставляет поле открытым, Escape закрывает), удаление подтверждается вторым нажатием того же пункта меню.
- **Заголовок карточки** (`#ct`) — не текст, а `input`: название правится на месте. Тесты читают `.value`, не `.textContent`.
- **Экранирование** — любой пользовательский текст в HTML только через `esc()`. Строки собираются конкатенацией, так что забытый `esc` — это XSS.

## Подключение модели

Замысел целиком — в `CONCEPT.md` (четыре этапа), текст промта — в `worker/PROMPT.md`. **Сделаны этапы 1 и 2: живые ответы и управление задачей.** Файлов, памяти, выжимок, токенов доступа и экрана настроек ещё нет.

- **`API`** — константа наверху блока «чат» в `app.js`. Пустая строка означает «сервера нет»: отвечает `stubReply()`, приложение остаётся рабочим.
- **Промт собирается на сервере** из четырёх блоков в строгом порядке: правила → профиль → снимок задачи → окружение (`worker/prompt.js`). Кэш-барьеры (`cache_control`) стоят после первых двух: правила общие для всех, профиль свой у каждого. Один барьер после профиля не годится — любая запись в память рвала бы весь кэш. **В блок правил нельзя подставлять ничего переменного**, включая дату: это ломает кэш при каждом запросе. Тест это проверяет.
- **Календарь строит воркер**, а не модель: дни недели она считает плохо. Клиент присылает свою дату (`today`) — у него и у сервера сутки могут не совпасть; воркер отклоняет расхождение больше суток.
- **Идентификаторы** короткие и стабильные: `t12` у задачи, `p8` у проекта, `s2` у шага. Модель ссылается только на них — ссылки по названию ломаются на дубликатах. Собирает их `chatPayload()` из `S`, отдельного поля в модели данных нет.
- **Снимок задачи пересобирается на каждый запрос**, поэтому чат всегда говорит о том, что человек видит на экране. У шага отдельного чата нет: переписка одна на задачу, а строка «открыт из шага» говорит модели, про какой шаг спрашивают.
- **Ответ идёт потоком.** Воркер пересобирает SSE Anthropic в свой формат (`text`, `error`, `done` с расходом токенов) — чтобы клиент не зависел от внутренних типов событий API. Клиент дорисовывает последний элемент ленты на ходу: пересобирать её целиком на каждый кусок нельзя, слетят прокрутка и анимации.
- **Повтор.** Перегрузка модели и обрыв потока — до трёх попыток с нарастающей паузой, но **только пока ничего не показано**: иначе кусок текста задвоится. Остальные ошибки показываются сразу отдельной строкой в ленте (`.ans.err`), а не всплывашкой.
- **Разметка.** `md()` в `app.js` — свой маленький рендерер: абзацы, списки, жирный, код, заголовки, таблицы, ссылки. **Порядок строгий: сначала `esc()` всего текста, потом разметка** — иначе ответ модели становится XSS. Ссылки только `http(s)` и `mailto`, в новой вкладке с `rel="noopener"`; таблица в контейнере с прокруткой, иначе растянет ленту на телефоне. Тесты проверяют и разметку, и попытки пролезть тегом, `javascript:` и кавычкой из атрибута.
- **Модель** — `claude-sonnet-5`, переопределяется переменной окружения `CHAT_MODEL`. Так решено в `CONCEPT.md`: Sonnet для разговора, Haiku для выжимок (этап 4).

### Инструменты (этап 2)

- **Исполняет их браузер, а не сервер.** Описания для модели — в `worker/tools.js` (уходят в поле `tools`, попадают в тот же кэшируемый префикс, значит между запросами меняться не должны). Исполнение — таблица `ACT` в `app.js`. У инструментов и у кнопок **один и тот же код изменения состояния** (`mark`, `inPj`, `S.seq`), иначе анимации и тесты разъедутся.
- **Отмена у каждого изменения.** Обёртка `act(label, apply, revert)` кладёт запись в стек `undos` и возвращает подпись для карточки. Стек живёт **только до перезагрузки страницы** — после неё записи нет и кнопка просто не рисуется. Хранить снимки дольше нельзя: вместе с задачей уходят переписка и вложения.
- **Пометка об отмене.** Отмена расходится с историей модели: там уже лежит «сделал». Поэтому `undoAct` готовит `undoNote`, и она уходит в начале следующего сообщения пользователя — иначе модель удивится расхождению и повторит действие.
- **Корзина, а не стирание.** `task_delete` и `task_delete_step` ставят `del` со временем. Удалённое пропадает из списков (`inPj`, `openIn`, `paint`, `chatPayload`), но `byId` и `prById` его находят — иначе не сработала бы отмена. `purge()` при загрузке стирает то, что старше `TRASH_DAYS`.
- **Лимит `MAX_ACTS` = 5 изменяющих вызовов на ответ, считает клиент.** Чтение (`task_search`, `chat_search`) не в счёт, иначе разведка съедает бюджет на действия. Промт повторяет то же число, но источник правды — код.
- **Хвостовые вызовы.** Если ход модели закончился только изменениями, результат ей не нужен — круг не продолжаем, и `tool_result` уйдёт вместе со следующим сообщением пользователя. Каждый круг это новый запрос с полным промтом, так что экономия заметная.
- **Переписка хранится блоками.** Запись в `item.chat` вида `{a, tu, res, cards}` — это один ход модели: текст, вызовы, результаты и карточки. `chatMessages()` разворачивает её в формат Anthropic: ход с `tool_use` и ответ с `tool_result` — два соседних сообщения с общим идентификатором вызова.
- Развёртывание — `worker/README.md`. Проверка без настоящего ключа — `npm run test:worker`: он подменяет поток Anthropic и проверяет сборку промта, календарь, стриминг и то, что поля из тела клиента не подменяют настройки воркера.

Всё остальное — `ask()`, отрисовка, «печатает…» — от подключения не зависит.

## Под устройства

- **Безопасные зоны.** В обоих HTML стоит `viewport-fit=cover`, поэтому отступы обязаны учитывать вырез и полосу дома: `max(базовый, env(safe-area-inset-*))`. В `panels.html` это падинг `.app`, в `index.html` — падинг каждого экрана `.scr`. Уберёшь `max()` — на iPhone контент уедет под вырез.
- **Страница не прокручивается.** `body{position:fixed;inset:0}` плюс `overscroll-behavior:none` — это убирает резинку всей страницы и pull-to-refresh на iOS. Прокручиваются только `.bd`, у них `overscroll-behavior:contain`, чтобы прокрутка не перекидывалась на соседнюю панель.
- **Размер полей ввода — 16 px и не меньше.** Ниже этого Safari зумит страницу при фокусе. `--fs-md` как раз 16.
- **Цели нажатия.** При `pointer:coarse` кнопки поднимаются до 44 px; мышью они остаются 36 px. Проверять при добавлении новых контролов.
- **Долгое нажатие.** У строк, кнопок и подписей `-webkit-touch-callout:none` и `user-select:none`, иначе iOS показывает меню и выделяет текст. Переписка и поля ввода из этого исключены — оттуда копируют.
- **Ширина.** `index.html`: панель и плашка не шире `--max` (720 px) по центру; до 760 px отступы от краёв и зазоры 8 px, дальше 16 и 12. `panels.html`: до 760 px панели стопкой, 761–900 px список ужимается до 280 px в пользу чата, дальше обычные 400 px. Меню действий до 760 px прижато к низу экрана, дальше — по центру окна.

## Дизайн

- Свои сообщения в чате (`.bub.mine`) — системный шрифт, белый текст на акцентном фоне, правый верхний угол острый; вопрос-приглашение в начале ленты — обычный `.bub`.
- Кнопки у полей ввода (`.ib`) круглые. Кнопка строки ввода (`.ib` в `.ftr`) заливается акцентом, пока в строке фокус (`:focus-within`).
- Акцент — фирменный `#0000FF` (`--text-accent`), один и тот же в светлой и тёмной теме: прогресс кольца, фокус, частицы, иконка вложения. У подписей-состояний (`tail`) иконок нет ни в списке, ни у шагов в чате проекта — только цветной текст. Текстом акцент не набирать — на чёрном у `#0000FF` контраст около 2.4:1.
- Светлая палитра по умолчанию, тёмная по `prefers-color-scheme` — максимально тёмная: фон `#000`, панели `#0a0a0a`, поля и пузыри `#141414`, границы `#222`. На чёрном тень не видна, поэтому край выезжающего чата в тёмной теме — волосяная линия (`--shadow-edge`). `theme-color` в обоих HTML для тёмной схемы тоже `#000000`. Все цвета — токены в `:root`, ни одного значения инлайном.
- Сетка 8 px, типографика в четыре ступени (12/14/16/20), название задачи в шапке чата (`.ct`) — `--fs-card` 24 px, зона нажатия 48 px, строка списка 64 px, строка шага 56 px. Шапка панели `--hd` одной высоты у «Входящих» и у карточки чата (три строки карточки плюс отступы: 104 px, на телефоне 96 px) — чтобы при переходе и в `panels.html` шапки совпадали. Меняются только в `:root`.
- Названия в строках (`.t1`: задачи, проекты, шаги, выполненные) — полужирные, 600; проект от задачи отличает иконка, а не начертание.
- Границы `0.5px` — так они остаются волосяными на плотных экранах.
- Шрифтов два, токены `--font-pixel` и `--font-text`. Заголовки — пиксельный `Pixelizer.ttf` (лежит рядом с HTML, `@font-face` в начале `app.css`, в HTML — `preload`): логотип `.logo`, «Входящие» `.ttl`, вся шапка карточки чата — крошка `.crumb`, название `.ct`, мета `.cm`, названия шагов в чате проекта (`.t1`) и маркер «>» в списке, а также все поля ввода (`input`: «Новая задача», «Спросить Claude», шаг проекта). Названия задач на странице задач (`#list .t1`) — системный, полужирный 600, маркер «>» у них остаётся пиксельным (`#list .ki`). Цифры тоже пиксельные: счётчик задач `.cnt` в шапке списка и число оставшихся шагов в кольце `.ring`. Всё остальное — подписи, переписка, меню — системный шрифт (`body`): на iPhone и Mac это SF Pro Text. Файл SF Pro в приложение не кладём: лицензия Apple разрешает шрифт только на устройствах Apple и не разрешает выкладывать его на сайт; на Android и Windows будет их системный шрифт. У Pixelizer одно начертание Bold, поэтому `font-weight:100 900` — без поддельного полужирного; знаков `→ … — « » №` в нём нет, они берутся из системного. Пиксель Pixelizer — 1/16 em: идеально чётко на 16 px.
- Иконки пиксельные, 8×8, монохромные (`currentColor`), размер 12 в подписях и строках списка, 16 в кнопках и меню (токены `--icon` / `--icon-lg`). Рисуются строками из `#` и `.` в `P`, `I(name, size, colorVar)` собирает SVG из прямоугольников; размер подгоняется под `devicePixelRatio`, чтобы пиксель иконки был целым числом физических пикселей (на iPhone 12 → 13⅓ px), иначе края размываются. Новая иконка — 8 строк по 8 символов.

## Как вносить изменения

- Правки точечные, файлы целиком не переписывать.
- После правки — `node --check app.js` и `npm test`. Тесты гоняют обе оболочки, поэтому ломающая правка в движке всплывает сразу.
- Состояние наружу отдаётся через `window.app` (геттер на `S` плюс основные функции) — это поверхность для тестов и консоли, в логике приложения ей пользоваться не надо.
- Новый файл в раздаче → допиши его и в `sw.js` (`ASSETS`), и в шаг «Собрать сайт» в воркфлоу, и подними версию кэша `V` в `sw.js`.
- **Обновление должно доезжать до телефона.** Pages отдаёт файлы с `cache-control: max-age=600`, а обычный `fetch` внутри service worker идёт через HTTP-кэш браузера — поэтому в `sw.js` стоит `fetch(request,{cache:'reload'})`. Уберёшь — установленное приложение будет до десяти минут (на iOS дольше) исполнять старый код, и правка «не приедет» без всяких признаков ошибки. Страница перезагружается сама при смене управляющего воркера, но только если он уже был: при первой установке `controllerchange` тоже срабатывает.
- Новые фичи сначала предлагать вариантами (3–5), реализовывать выбранный.
