# Задачи — список с чатом по каждой задаче

Список задач и проектов, где задачу можно закрыть галочкой, а можно «толкать вперёд» перепиской. Большие задачи становятся проектами: в списке видна одна строка проекта со следующим шагом.

Живёт на GitHub Pages: https://cucujahx-coder.github.io/CLUTCH/

## Стек и запуск

- Статические файлы, **сборки нет**. Ванильный JS, без фреймворков и рантайм-зависимостей. Иконки — штриховые SVG 24×24: путь лежит в `P`, собирает `Ic(path, size)`.
- `npm start` — раздать папку локально. `npm test` — тесты приложения (jsdom) и воркера. По отдельности: `npm run test:app`, `npm run test:worker`.
- Проверка синтаксиса без запуска: `node --check app.js`.
- Деплой: `git push` в `main` → `.github/workflows/deploy.yml` гоняет тесты и выкладывает на Pages. В артефакт файлы перечислены явно — **добавил новый файл, допиши его в шаг «Собрать сайт»**, иначе на проде его не будет. Папка `worker/` на Pages не выкладывается и не должна: она разворачивается отдельно в Cloudflare — `npm run deploy:worker` из любой папки репозитория. Запускать `wrangler deploy` вручную из корня нельзя: конфига воркера там нет, wrangler примет репозиторий за статический сайт, создаст `wrangler.jsonc`, пропишет свои скрипты в `package.json` и попробует выложить всё вместе с `node_modules`. Уже наступали.

## Две оболочки, один движок

`index.html` (экран списка и экран чата друг над другом) и `panels.html` (те же два экрана рядом) — тонкие обёртки вокруг общих `app.js` и `app.css`. Оболочка задаёт `window.MODE` (`nav` | `two`) перед подключением скрипта, `app.js` по нему выбирает `shellNav()` или `shellTwo()`. Разметка у обеих одинаковая, различий два: класс на `<body>` и функции `open`/`back`. В `two` экраны стоят колонками (`body.two .phone{display:flex}`), уже 760 px — снова стопкой с переходом.

Внутри экрана всё абсолютное: полосы затемнения, таблетка логотипа (или названия), угловые круглые кнопки, прокрутка `.scroll` во всю высоту и нижний блок. Прокручиваются только `.scroll`, страница зафиксирована.

Логику писать только в `app.js`. Если правка нужна в обоих HTML — почти наверняка она на самом деле в движке.

## Модель данных

Всё состояние — один объект `S`, целиком в `localStorage` под ключом `tasks:v1`.

```js
S = {
  seq,                       // счётчик id, общий для задач и проектов
  ts: [{                     // задачи и шаги проектов — одним списком
    id, t,                   // t — название
    due: "YYYY-MM-DD"|null,
    pj: id|null,             // id проекта, если это шаг
    done: 0|1, doneAt,
    kind: 'task'|'reminder'|'routine'|'call'|'meeting'|'payment'|'purchase'|'mail'|'idea' | undefined,
                             // тип задачи (подпись для диктора); нет поля — угадывается по названию (kindOf)
    tail: {k:'art'|'wait'|'dec', x} | null,   // подпись-состояние в строке
    pri: 0|1|2|3|4,          // приоритет, кольцо в кружке строки
    del,                     // время удаления: корзина, а не стирание
    t0,                      // исходное название, если его сократили до двух слов
    files: [{name, mime, size, body?}],       // файлы задачи; body только у мелких
    sum, sumTo,              // выжимка старой части переписки и докуда сжато
    n,                       // счётчик сообщений для подписи
    a,                       // последняя реплика ассистента, показывается вверху чата
    chat: [{u, att?}|{a, tu?, res?, cards?}|{typing}|{err, a}]
  }],
  pr: [{ id, n, due, why, pri, del, chat }],  // проекты; n — название, why — «что мешает»
  showDone, cur: {k:'t'|'p', id},
  mem: [строки],             // память ассистента, общая на все задачи
  spend: {in, out, cr, cw}   // израсходованные токены по четырём категориям
}
```

- `pj` хранит **id** проекта, не индекс: индексы ломались бы при удалении.
- `done` меняется только через `mark(x, done)` — он же ставит и обнуляет `doneAt`.
- `OLD_KEYS` — ключи приложений-предшественников (`clutch:v5` и старше). Если `tasks:v1` пуст, `importOld()` один раз перечитывает их и раскладывает в новую модель. Меняешь ключ — допиши старый в этот список, иначе у людей молча пропадут задачи.
- `save()` дебаунсит запись на 120 мс, `flush()` пишет сразу; `flush` висит на `pagehide` и `beforeunload`.
- Первый запуск без данных — `seed()`, демо-набор с датами относительно сегодня.

## Ключевые механики

Раскладка «как в камере»: содержимое проезжает под полупрозрачными полосами (`.veil`), управление живёт по углам и снизу.

- **Шапка списка** — по центру сверху закреплённая таблетка с логотипом CLUTCH (PNG вшит в HTML, перекрашен в `--text`), справа круглая кнопка сортировки по приоритету (`#sort`). Нажатие на таблетку открывает настройки. Отдельной шапки «Входящие», счётчика и фильтров нет.
- **Нижний блок** (`.dock`) — большая кнопка 76 px с пауком (`#shutter`, `--hot`), под ней кружок `#find`: переключает входящие ↔ выполненные (`S.showDone`). Зазоры 21 px по геометрии — это ровно 16 px до видимого кольца кнопки, которое рисуется внешней тенью и места не занимает.
- **Строка ввода** (`.composer`) в свёрнутом виде отсутствует: её разворачивает нажатие на паука (`openComposer`, фокус ставится синхронно внутри жеста, иначе iOS не покажет клавиатуру), закрывает пустой ввод, Escape или добавленная задача. Пока она открыта, док спрятан, у прокрутки класс `.tight`, а нижняя полоса затемнения ниже.
- **Плашка о выполненном** (`.toast`) вырастает из кружка `#find`, живёт 4 секунды, «Вернуть» откатывает. При открытой клавиатуре не показывается — и ещё 1,2 с после её ухода (`kbOpen`, `kbLast`): первое касание убирает клавиатуру, и к моменту показа фокуса уже нет.
- **Приоритет** — четыре ступени, все плотные и разного тона: `--pri1` #2EC27E, `--pri2` #FFD400, `--pri3` #FF9500, `--pri4` #FF4500; кольцом внутри кружка строки. Долгое нажатие по строке (500 мс, сдвиг больше 10 px — прокрутка; правая кнопка мыши — то же) открывает на её месте капсулу из пяти кружков: «нет» и четыре цвета. Другого меню действий нет — срок, проект, удаление делаются из чата.
- **Строка проекта** — показывает следующий открытый шаг, в кружке число открытых. Нажатие закрывает именно этот шаг, строка остаётся на месте.
- **Список прижат к строке ввода, а не к верху экрана.** Самое свежее ближе к пальцу: добавил задачу — остальные ушли вверх. Держится это двумя вещами сразу, и обе нужны. Распорка `.spacer{flex:1 0 auto}` перед `#list` прижимает короткий список к низу; `toBottom()` в конце `paint(keep)` без `keep` доводит до низа длинный. Убирали и то и другое — список встал сверху, и новые задачи стали уходить под док, где их не видно. У ленты переписки распорка ровно та же и по той же причине.
- **Перед правкой `scrollTop` читается `offsetHeight`.** Без этого браузер ещё не применил новые размеры, `scrollTop` обрежется по старым, и только что добавленная задача останется за краем. Та же грабля, что в `trackVH`.
- **Смена `.tight` меняет запас снизу**, поэтому `openComposer` и `closeComposer` зовут `toBottom()` — иначе после разворота строки ввода список остаётся не доехавшим.
- **Экран чата** — та же шапка: слева круглая кнопка «назад», справа круглая кнопка выполнения (`#hctl`, у проекта в ней число открытых шагов), по центру таблетка с названием задачи (`#ct` — input, правится на месте, Play Bold 17). Шаги проекта идут карточками `.step` в начале ленты.
- **Паучок-курсор** — один на всю ленту: бежит за печатающимся ответом (26 мс на знак, пробел ×1.4, `.,—:` ×7) и остаётся сидеть в конце последнего ответа. Ответ ассистента печатается по буквам (`typeInto`), новые реплики всплывают без отскока (`.rise`), лента доезжает до низа плавной прокруткой.
- **Клавиатура в чате** — после отправки не прячется: у кнопки перехвачен `pointerdown`, фокус остаётся в поле. Убирает её касание или прокрутка самой переписки.
- **Анимация выполнения** — общая функция `burst(row, keepRow)`: хлопок `pop()` (синтез Web Audio), призрак строки уходит в размытие и свет, у кружка вспышка `.rflash`, расходящееся кольцо `.ringfx` и десять искр. `keepRow` — строка остаётся (шаг проекта из списка), тогда вместо призрака вспыхивает сама плашка. Через 140 мс модель меняется и список перерисовывается.
- **Засветка нажатия** (`elflash`) — только внутренняя белая заливка на 220 мс. Анимировать `filter` нельзя: Safari от этого пересчитывает все `backdrop-filter` на экране, и вместе с кнопкой вспыхивает таблетка логотипа. Строка ввода при активации получает бегущую слева направо полосу (`sweep`, 460 мс).
- **Тактильность** — `tap(ms)`: 6 перелистнуть, 8 открыть, 14 отправить, 25 выполнить. Android — `navigator.vibrate`, iPhone — щелчок скрытого `<input type="checkbox" switch>` внутри `<label>` (Safari 17.4+), тяжёлые значения повторяются через 45 и 90 мс.
- **Отдача забирает фокус, и это ломало клавиатуру.** Клик по `<label>` в WebKit не только переключает контрол, но и переводит на него фокус. Строка новой задачи разворачивалась так: фокус в поле → `tap(8)` — и фокус тут же уходил в скрытый переключатель, iOS считала поле неактивным и клавиатуру не показывала. В отладке это видно как «фокус в поле» и сразу «фокус ушёл». Лечится двумя мерами сразу, обе нужны: `tap()` запоминает активный элемент и возвращает ему фокус после щелчка (это закрывает и чат, где отдача идёт при отправке), а в `openComposer` отдача вызывается **до** `focus()`, чтобы последним действием жеста остался именно фокус. В примерке тот же код работал, потому что переключатель лежал в разметке с самого начала; в приложении он создаётся при первом нажатии и ровно тогда перехватывает фокус. Тест воспроизводит поведение WebKit руками и падает, если убрать любую из двух мер.
- **Высота окна и клавиатура.** `.phone` — это `position:fixed; top:var(--vvtop); height:var(--vh)`, то есть контейнер приложения равен видимой области. Композер лежит на его дне и оказывается над клавиатурой сам. **Никакой высоты клавиатуры в раскладке нет и быть не должно** — переменную `--kb` из движка убрали дважды. Безопасные зоны меряются один раз пробником в `--safe-t` / `--safe-b`: `env()` внутри `calc()` из JS не прочитать.
- **События iOS — вспомогательный сигнал, а не источник истины.** `trackVH()` сверяется с фактическими размерами каждый кадр, пока идёт ввод **или пока клавиатура на экране** (`kbUp()`: `innerHeight - visualViewport.height > 80`). Второе условие ключевое: оно не даёт застрять в поднятом состоянии, даже если событие не пришло — а при скрытии клавиатуры их может не прийти ни одного, и раскладка оставалась поднятой, накладывая блоки друг на друга. Цикл останавливается сам, когда высота вернулась. Вне ввода — обычные события (`resize` и `scroll` у `visualViewport`, `resize` и `orientationchange` у окна).
- **Значения — чистая функция текущего состояния**, без накопленных дельт: пропущенное обновление не оставляет следа. Это то, что в прошлых версиях ломалось чаще всего.
- **Низ содержимого держится на месте.** Когда область ужимается под клавиатуру, `trackVH()` сдвигает `scrollTop` всех `.scroll` ровно на разницу высот — иначе список и лента съезжают вверх на высоту клавиатуры и прячут то, что было у поля ввода. Перед правкой прокрутки читается `offsetHeight`, чтобы браузер применил новую высоту: иначе `scrollTop` обрежется по старым размерам.
- **Тупики, проверенные на устройстве.** Первый: поднимать композер на вычисленную высоту клавиатуры (переменная `--kb`, отступ снизу у прокрутки и дока) — поле «гуляет», потому что высота клавиатуры не описывает реальный сдвиг. **На эти грабли наступали дважды: во второй раз они приехали вместе с новым дизайном.** Второй: не компенсировать смещение вовсе — шапка и список уезжают выше края экрана. Третий: обновлять смещение только по `resize` — оно протухает. iOS панорамирует при фокусе (`offsetTop` становится, скажем, 186), а возвращает в ноль уже событием `scroll`; контейнер остаётся опущенным, и композер уходит под клавиатуру. Проверено снимком с телефона: `offsetTop 0` при `--vvtop 186px`.
- **Как отлаживать.** Открыть страницу с `?debug` — поверх интерфейса появятся живые числа: размеры окна и видимой области, смещение, значения переменных, положение контейнера и композера, элемент в фокусе и трасса последних высот с буквой события (`r` — resize, `s` — scroll, `w` — окно, `f` — кадр, `i` — старт). Снимок экрана с открытой клавиатурой отвечает на вопрос сразу; словесные описания дважды приводили к половинчатым правкам.
- **Что не делать с клавиатурой.** Грабли, на которые наступали:
  1. Переход (`transition`) на движении композера. `visualViewport` шлёт `resize` десятками за время выезда клавиатуры, анимация гонится за новой целью и не успевает встать.
  2. Подгонка `scrollTop` на каждом событии — список идёт ступеньками.
  3. Прятать и телепортировать поле на время фокуса, чтобы iOS не прокрутил страницу к нему: поле мигало на каждом тапе.
  4. `window.scrollTo(0, 0)` при фокусе — борется с панорамированием, которое и так учтено через `--vvtop`.
- В обоих HTML у viewport стоит `interactive-widget=resizes-content`. Где поддерживается, слой раскладки ужимается сам и `--vvtop` остаётся нулём; где нет — работает модель выше. Одно другому не мешает.
- **Переход между экранами** — CSS по классу `.on` у `#scr-detail`, список уезжает влево (`.away`). Назад — стрелка, Esc или свайп вправо от левого края (зона 28 px).
- **Скрепка и вложения.** Одно скрытое `#pick` на обе строки ввода: диалог выбора всё равно один на экран, а два поля пришлось бы держать в синхроне. В чате вложение ложится в `pending` и уходит с ближайшим сообщением. У строки новой задачи цели ещё нет — файлы ждут в `ntPick`, и после добавления задача открывается сама, иначе вложение уехало бы в первую попавшуюся переписку. **Пока открыт системный выбор файла, строку ввода закрывать нельзя** (флаг `picking`): поле теряет фокус, и без флага выбранный файл вернулся бы в уже свёрнутый композер.
- **Высота чипов не угадывается формулой** — они переносятся по строкам. `drawChips` меряет блок и кладёт результат в `--pend` своего экрана; на эту величину поднимается дно прокрутки и нижняя полоса затемнения. Без этого лента лезет под чипы.
- **Настройки** открываются нажатием на таблетку с логотипом: памяти, расходу и корзине больше негде быть. Накладка `.sheet.set`, одинаковая в обеих оболочках, — третий экран сломал бы логику переходов.
- **Экранирование** — любой пользовательский текст в HTML только через `esc()`. Строки собираются конкатенацией, так что забытый `esc` — это XSS.

## Подключение модели

Замысел целиком — в `CONCEPT.md` (четыре этапа), текст промта — в `worker/PROMPT.md`. **Сделаны все четыре этапа.** Не сделаны только токены доступа с лимитом в деньгах на Durable Object — воркер защищён проверкой `Origin`, которая не спасает от curl.

- **`API`** — константа наверху блока «чат» в `app.js`. Пустая строка означает «сервера нет»: отвечает `stubReply()`, приложение остаётся рабочим.
- **Промт собирается на сервере** из четырёх блоков в строгом порядке: правила → профиль → снимок задачи → окружение (`worker/prompt.js`). Кэш-барьеры (`cache_control`) стоят после первых двух: правила общие для всех, профиль свой у каждого. Один барьер после профиля не годится — любая запись в память рвала бы весь кэш. **В блок правил нельзя подставлять ничего переменного**, включая дату: это ломает кэш при каждом запросе. Тест это проверяет.
- **Календарь строит воркер**, а не модель: дни недели она считает плохо. Клиент присылает свою дату (`today`) — у него и у сервера сутки могут не совпасть; воркер отклоняет расхождение больше суток.
- **Идентификаторы** короткие и стабильные: `t12` у задачи, `p8` у проекта, `s2` у шага. Модель ссылается только на них — ссылки по названию ломаются на дубликатах. Собирает их `chatPayload()` из `S`, отдельного поля в модели данных нет.
- **Снимок задачи пересобирается на каждый запрос**, поэтому чат всегда говорит о том, что человек видит на экране. У шага отдельного чата нет: переписка одна на задачу, а строка «открыт из шага» говорит модели, про какой шаг спрашивают.
- **Ответ идёт потоком.** Воркер пересобирает SSE Anthropic в свой формат (`text`, `error`, `done` с расходом токенов) — чтобы клиент не зависел от внутренних типов событий API. Клиент дорисовывает последний элемент ленты на ходу: пересобирать её целиком на каждый кусок нельзя, слетят прокрутка и анимации.
- **Повтор.** Перегрузка модели и обрыв потока — до трёх попыток с нарастающей паузой, но **только пока ничего не показано**: иначе кусок текста задвоится. Остальные ошибки показываются сразу отдельной строкой в ленте (`.ans.err`), а не всплывашкой.
- **Разметка.** `md()` в `app.js` — свой маленький рендерер: абзацы, списки, жирный, код, заголовки, таблицы, ссылки. **Порядок строгий: сначала `esc()` всего текста, потом разметка** — иначе ответ модели становится XSS. Ссылки только `http(s)` и `mailto`, в новой вкладке с `rel="noopener"`; таблица в контейнере с прокруткой, иначе растянет ленту на телефоне. Тесты проверяют и разметку, и попытки пролезть тегом, `javascript:` и кавычкой из атрибута.
- **Модель** — `claude-sonnet-5`, переопределяется переменной окружения `CHAT_MODEL`. Так решено в `CONCEPT.md`: Sonnet для разговора, Haiku для выжимок (этап 4).

### Инструменты (этап 2)

- **Исполняет их браузер, а не сервер.** Описания для модели — в `worker/tools.js` (уходят в поле `tools`, попадают в тот же кэшируемый префикс, значит между запросами меняться не должны). Исполнение — таблица `ACT` в `app.js`. У инструментов и у кнопок **один и тот же код изменения состояния** (`mark`, `inPj`, `S.seq`), иначе анимации и тесты разъедутся.
- **Отмена у каждого изменения.** Обёртка `act(label, apply, revert)` кладёт запись в стек `undos` и возвращает подпись для карточки. Стек живёт **только до перезагрузки страницы** — после неё записи нет и кнопка просто не рисуется. Хранить снимки дольше нельзя: вместе с задачей уходят переписка и вложения.
- **Пометка об отмене.** Отмена расходится с историей модели: там уже лежит «сделал». Поэтому `undoAct` готовит `undoNote`, и она уходит в начале следующего сообщения пользователя — иначе модель удивится расхождению и повторит действие.
- **Корзина, а не стирание.** `task_delete` и `task_delete_step` ставят `del` со временем. Удалённое пропадает из списков (`inPj`, `openIn`, `paint`, `chatPayload`), но `byId` и `prById` его находят — иначе не сработала бы отмена. `purge()` при загрузке стирает то, что старше `TRASH_DAYS`.
- **Лимит `MAX_ACTS` = 5 изменяющих вызовов на ответ, считает клиент.** Чтение (`task_search`, `chat_search`) не в счёт, иначе разведка съедает бюджет на действия. Промт повторяет то же число, но источник правды — код.
- **Хвостовые вызовы.** Если ход модели закончился только изменениями, результат ей не нужен — круг не продолжаем, и `tool_result` уйдёт вместе со следующим сообщением пользователя. Каждый круг это новый запрос с полным промтом, так что экономия заметная.
- **Переписка хранится блоками.** Запись в `item.chat` вида `{a, tu, res, cards}` — это один ход модели: текст, вызовы, результаты и карточки. `chatMessages()` разворачивает её в формат Anthropic: ход с `tool_use` и ответ с `tool_result` — два соседних сообщения с общим идентификатором вызова.

### Файлы (этап 3)

- **Где что лежит.** Задачи остаются в `localStorage` — они маленькие и нужны мгновенно при старте. Тела файлов туда не помещаются (лимит около 5 МБ и синхронный доступ), поэтому уезжают в IndexedDB (`clutch` / `files`, ключ `t12/имя.md`). В состоянии задачи остаётся только `files: [{name, mime, size, body?}]` — **благодаря этому снимок задачи собирается синхронно** и не тянет за собой весь код.
- **`body` есть только у файлов до `INLINE` (2 КБ).** Такие уходят в промт целиком блоком `<file>`, чтобы «поправь второй абзац» не стоило лишнего круга. У больших в состоянии только имя и размер, содержимое модель берёт через `file_read`.
- **Размер считается в байтах**, а не в символах: кириллица в UTF-8 занимает по два, и по этому числу решается, вкладывать файл в промт или нет. `bytes()` пробует `TextEncoder`, потом `Blob` — в jsdom первого нет.
- **Существующий файл не перезаписывается без `overwrite`** — так же, как удаление требует подтверждения. Слеши из имени вырезаются, чтобы имя не уводило из задачи.
- **Скачивание через Blob**: файла на сервере нет, он живёт только в браузере.
- **Исполнение инструментов асинхронно** (`runTool` всегда возвращает обещание) — иначе чтение из IndexedDB не встроить. Тесты это ожидают.

### Вложения от пользователя

- **Картинки сжимаются** до мегапикселя и в JPEG перед сохранением, PDF ограничен 5 МБ: это base64 в переписке, и без мер он уезжает заново каждый ход.
- **Вложение старше `ATT_TURNS` (5) ходов заменяется в истории ссылкой** — сам файл остаётся в задаче, из контекста уходит. Ходы считаются с конца по хвосту переписки.
- Тела вложений лежат в IndexedDB под ключом `t12/att:имя`, отдельно от текстовых файлов задачи.

### Короткие названия

- **Название задачи — два слова, максимум три.** Пользователь пишет как придётся, а в списке имя должно читаться с одного взгляда. Работает в двух местах: правило в промте (задачи, которые заводит модель) и `shortenTitle()` при добавлении из списка — отдельный дешёвый вызов на воркер (`{shorten}` → Haiku).
- **Источник правды — код, а не промт.** `tidyTitle()` снимает кавычки и точку и режет до `TITLE_WORDS` слов: модель периодически отвечает длиннее, чем просили.
- **Исходник сохраняется в `t0`** — ничего не теряется, и повторно задачу уже не сокращаем.
- **Три случая, когда не трогаем:** название и так в два слова (запрос не тратим), нет сети (остаётся как набрали), название успели поправить руками, пока шёл запрос — для этого оно запоминается **до** запроса и сверяется после.

### Память и выжимки (этап 4)

- **Память** — `S.mem`, массив строк, общий на все задачи. Пишет её модель инструментами `memory_write` / `memory_forget` (хвостовые, круга не стоят), уходит блоком `<profile>` перед кэш-барьером. Видна и стирается в настройках.
- **Выжимка.** Переписка длиннее `SUM_AFTER` (24) сжимается: `squeeze()` шлёт старую часть на воркер, тот дёргает Haiku и возвращает текст. Клиент кладёт его в `item.sum`, а `item.sumTo` помечает, докуда сжато — `chatMessages` шлёт только хвост. Не получилось сжать — просто продолжаем слать историю целиком.
- **Расход считается в деньгах, а не в токенах**: у чтения кэша, записи кэша, входа и выхода разные цены (`PRICE`). Числа берутся из `usage` в событии `done`. Поменяется модель — поменять цены.
- **Настройки** — накладка, одинаковая в обеих оболочках (вход — таблетка с логотипом в шапке списка). Память со стиранием, расход, корзина с возвратом, «стереть все данные» в два нажатия, строка про приватность. Сделана накладкой, а не третьим экраном, чтобы не трогать логику переходов.
- Развёртывание — `worker/README.md`. Проверка без настоящего ключа — `npm run test:worker`: он подменяет поток Anthropic и проверяет сборку промта, календарь, стриминг и то, что поля из тела клиента не подменяют настройки воркера.

Всё остальное — `ask()`, отрисовка, «печатает…» — от подключения не зависит.

## Под устройства

- **Безопасные зоны.** В обоих HTML стоит `viewport-fit=cover`. Отступы считаются от `--safe-t` / `--safe-b`, которые движок меряет пробником на старте (`trackSafe`), плюс боковые `max(16px, env(safe-area-inset-*))` у экрана.
- **Страница не прокручивается.** `body{position:fixed;inset:0}` и `overscroll-behavior:none` убирают резинку и pull-to-refresh; у `.scroll` — `overscroll-behavior:contain`.
- **Размер полей ввода — 16 px и не меньше**, иначе Safari зумит страницу при фокусе.
- **Цель нажатия 44 px.** Проверять при добавлении новых контролов.
- **Долгое нажатие.** У строк и кнопок `-webkit-touch-callout:none` и `user-select:none`; переписка и поля ввода из этого исключены — оттуда копируют.
- **Клавиатура.** Контейнер приложения ужимается до видимой области (`--vh` / `--vvtop`), поэтому строка ввода, док и плашка оказываются над клавиатурой сами — подробности в «Ключевых механиках». На iOS фокус ставится строго синхронно внутри жеста, иначе клавиатура не откроется.

## Дизайн

- Палитра Retro-Tech, одна тёмная тема: `--bg` #101010 фон, `--card` #242424, текст `--text` #E0E0E0, приглушённый `--muted` #8E8E8E, `--hot` #FF4500 (большая кнопка, кольцо срочного, искры), `--blue` #0000FF (активное: обводка строки ввода, включённые кнопки, свои реплики). Фиолетового из палитры нет.
- Все поверхности управления — стеклянные капсулы: полупрозрачный фон (таблетки и кнопки rgba(26,26,26,.72), строка ввода rgba(36,36,36,.72)), `backdrop-filter: blur(8–10px)` и кант `--glass` — чёткие линии в пиксель по диагонали: свет по левому верхнему и правому нижнему углу, тень по двум другим. Плашки задач и карточки шагов сделаны так же.
- Геометрия капсульная: строка 68 (44 + 11×2), радиус 28, кружки 44, большая кнопка 76, зазоры 8 между строками и 16 между блоками.
- Шрифтов два: `Play` (четыре файла `play-*.woff2` рядом с HTML) — весь текст; `Pixelizer.ttf` — заголовочный (`--font-head`), им набраны цифры в кружках и счётчики. Название задачи в шапке чата — Play Bold 17.
- Иконки — штриховые SVG 24×24 из `P`, собираются через `Ic(path, size)`; паук на большой кнопке и паучок-курсор нарисованы шестиугольниками (`SPIDER`, `SPIDER_JUMP`).
- Движение: `--ease-ios` для перемещений, `--bounce` для появления. Выполнение — исключение, оно резкое и почти мгновенное.

## Как вносить изменения

- Правки точечные, файлы целиком не переписывать.
- После правки — `node --check app.js` и `npm test`. Тесты гоняют обе оболочки, поэтому ломающая правка в движке всплывает сразу.
- Состояние наружу отдаётся через `window.app` (геттер на `S` плюс основные функции) — это поверхность для тестов и консоли, в логике приложения ей пользоваться не надо.
- Новый файл в раздаче → допиши его и в `sw.js` (`ASSETS`), и в шаг «Собрать сайт» в воркфлоу, и подними версию кэша `V` в `sw.js`.
- **Обновление должно доезжать до телефона.** Pages отдаёт файлы с `cache-control: max-age=600`, а обычный `fetch` внутри service worker идёт через HTTP-кэш браузера — поэтому в `sw.js` стоит `fetch(request,{cache:'reload'})`. Уберёшь — установленное приложение будет до десяти минут (на iOS дольше) исполнять старый код, и правка «не приедет» без всяких признаков ошибки.
- **Меняешь дизайн целиком — перечитай раздел про клавиатуру.** Новая раскладка почти наверняка придёт с моделью «поднять композер на высоту клавиатуры»: она выглядит очевидной и не работает. Так уже было.
- Новые фичи сначала предлагать вариантами (3–5), реализовывать выбранный.
